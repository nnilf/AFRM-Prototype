## Why it is needed

AFRM uses one groundspeed and one fuel flow for the whole flight. The baseline tests (`evidence/baseline_tests.txt`) found no calculation errors, so the biggest gap left is in the model itself.

The planned challenge test (`test_challenge.py`) shows the problem. A two-leg route gives 1800 kg arrival fuel and CAUTION when worked out leg by leg. If the user enters simple averages of the two legs, AFRM gives 2142.86 kg and NORMAL instead. The code is correct, as weighted averages give the right answer, but the user has to work those out by hand, and a mistake gives false reassurance.

## The change

A flight can have an optional ordered route of segments. Each segment has a distance (km), groundspeed (km/h) and fuel flow (kg/h).

For each segment:

- time = distance / groundspeed
- burn = fuel flow × time

Then arrival fuel = fuel − total burn, and flight time = total time.

New requirement **FR-06**: *If a flight has a route, AFRM calculates flight time and arrival fuel from its segments, then uses that arrival fuel for the reserve margin and fuel status.*

## Rules

| Topic | Rule |
|---|---|
| Segment values | Distance, groundspeed and fuel flow must all be numbers greater than zero |
| Empty route | A route with no segments raises `ValueError` |
| Input file | Optional `routes.csv` with columns `flight,distance_km,groundspeed_kmh,fuel_flow_kg_h`, one row per segment, in order |
| Running it | `python main.py routes.csv` uses routes, and plain `python main.py` works exactly as before |
| Flights without a route | Use the original single-segment calculation |
| Total distance | The segments must add up to the flight's `distance_km` within 0.001 km, otherwise the flight is `INVALID` |
| Margin and status | `reserve_margin` and `fuel_status` are reused unchanged, with the route arrival fuel |
| Endurance and range | Keep their original meaning, using the fuel flow and groundspeed in `flights.csv`. A route says nothing about the rate after arrival, so changing them would be guesswork. |
| NumPy | A new route function is added, and `calculate_batch` is not changed |

## Risks

- A mistake in the route sum would give wrong arrival fuel, which is the highest risk in `TEST_PLAN.md`.
- More inputs mean more validation rules and more code to maintain.
- Routes make scenarios more expressive, but they do not prove the model is accurate for real aircraft.
- The new `main.py` argument could change normal output if done wrong.

## Acceptance tests

These are written and committed before any of the change is implemented.

| Test | Pass if |
|---|---|
| `test_cr001_single_segment_matches_baseline` | One segment of 1200 km, 800 km/h and 2400 kg/h with fuel 6000 gives the same arrival fuel as `V1.0.1`, 2400 kg |
| `test_cr001_two_segments_matches_hand_values` | (400, 800, 2400) then (600, 600, 3000) gives 1.5 h and 4200 kg burn |
| `test_cr001_three_segments_matches_hand_values` | (300, 600, 2000), (400, 800, 2400) then (500, 500, 3000) gives 2 h and 5200 kg burn |
| `test_cr001_invalid_segments_rejected` | Zero, negative or non-numeric segment values, and an empty route, raise `ValueError` |
| `test_cr001_segment_status_correct` | The two-segment route with protected fuel 1500 kg gives CRITICAL at fuel 5699, CAUTION at 5700 and NORMAL at 6075 |
| `test_cr001_numpy_matches_python` | The NumPy route results match plain Python within 0.000001 and match the hand values |
| `test_cr001_route_distance_must_match` | A route that does not add up to the flight's distance prints `INVALID` |
| `test_cr001_cli_uses_route` | `main.run` with a route prints the route arrival fuel and status |

Also required:

- All the original tests still pass without being changed.
- `python main.py` without a route file gives byte-identical output to `V1.0.1`.
- Coverage targets in `TEST_PLAN.md` are still met.
- **Performance:** NumPy must process 100,000 three-segment routes in a median under 10 ms over 5 repeats, the same target as the baseline. This was set before any route code was measured.
